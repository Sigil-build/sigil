# Add an install step to Sigil

A step type crosses **nine layers**. Missing one produces a step that validates
but silently never runs (or packs but crashes the installer). Work in this order,
mirroring an existing step of similar shape (`HttpDownloadStep` for I/O + rollback,
`RegistryWriteStep` for Win32, `IniWriteStep` for config editing).

## The chain

1. **Typed model** — `src/SigilBuild.Core/Manifest/InstallStep.cs`
   Add a `public sealed record YourStep(...) : InstallStep(Id, When, OnFailure)`
   nested record. Keep parameters primitive/AOT-friendly.

2. **Parser + validation** — `src/SigilBuild.Core/Configuration/ManifestParser.cs`
   Per-step parameter validation lives HERE, not in the JSON schema (the schema
   intentionally uses a loose step shape and defers to the typed graph). Emit
   existing diagnostic codes from `src/SigilBuild.Core/Diagnostics/DiagnosticCodes.cs`:
   `SIG0230` unknown type, `SIG0231` parameter mismatch, `SIG0232` missing required
   field. New codes go in the SIG023x band with a named constant.

3. **JSON schema** — `schemas/sigil-schema.json`
   Add the snake_case type name to the step-`type` enum. **The enum is duplicated
   in multiple places** (pre_install / install_steps / post_install / option
   component blocks — grep for an existing type like `"file_copy"` and update
   every occurrence). The schema is embedded in `SigilBuild.Core` as an
   `EmbeddedResource`, so a rebuild picks it up — no codegen step.

4. **Blob serializer** — `src/SigilBuild.Wrapper.Core/Json/SerializableInstallStep.cs`
   Add the fields + discriminator handling. This type uses a **hand-rolled
   discriminator by design** (no `JsonDerivedType` — it pulls reflective
   polymorphism into the AOT graph). Follow the existing mapping pattern both
   directions (pack-time write in `SigilBuild.Packaging/ExeWrapper/`, runtime read).
   If you add new nested types, register them in `WrapperBlobJsonContext.cs`
   (`[JsonSerializable]`) or AOT deserialization fails at runtime, not compile time.

5. **Runtime step** — `src/SigilBuild.Wrapper.Core/Steps/YourStep.cs`
   Implement `IStep.RunAsync(StepContext, RollbackJournal, CancellationToken)`.
   Every mutating step MUST journal a reversal record (`SerializableRollbackRecord`
   discriminators) so failed installs roll back and uninstall works. Win32-bound
   steps go in `Steps/Win32/` and must be guarded for CA1416.

6. **Factory** — `src/SigilBuild.Wrapper.Core/Engine/StepFactory.cs`
   Add the arm to the `spec switch`. Forgetting this = `NotSupportedException`
   at install time.

7. **Wizard surface (only if UI-visible)** — if the step is auto-generated by an
   Options component, wire it in `SigilBuild.Installer.Host` (screens render from
   the manifest; see `Views/Screens/` + `InstallerViewModel`).

8. **Tests** (all three tiers)
   - `tests/SigilBuild.Core.Tests/Manifest/` — parse + validation diagnostics
   - `tests/SigilBuild.Schema.Tests/Fixtures/` — a fixture YAML using the step
   - `tests/SigilBuild.Wrapper.Tests/Steps/` — RunAsync happy path, failure,
     rollback journal contents, cancellation
   xUnit + FluentAssertions, AAA layout.

9. **Docs + examples** — `docs/guides/install-steps.md` (catalog entry),
   `docs/manifest-reference.md` (field table), and extend `examples/full/sigil.yaml`
   if the step is broadly useful (CI validates every example).

## Verify

```bash
dotnet build Sigil.slnx -c Release   # trim analyzer only runs in Release
dotnet test Sigil.slnx -c Release
```

On Linux sandboxes the Win32/registry/service tests can't run — say so in the PR
rather than claiming a full green suite.
